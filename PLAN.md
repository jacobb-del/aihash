# План: как строим

Документ решений. Не обзор вариантов — выбор сделан, причина указана. Всё, что здесь написано, можно оспорить, но по умолчанию делаем так.

Словарь наружу — по правилам из [PRODUCT_IDEA.md](PRODUCT_IDEA.md): **отпечаток**, **звено**, **цепь**, **пломба**, «видно, если трогали». Внутри документа для точности используются технические термины.

| Ключи | **нет ключей вообще**; подписи — опция сверху | Управление ключами убивает такие проекты; целостность их не требует |
| Хранение | обычные файлы на диске + опциональные WORM-приёмники | Читается через 7 лет без нашей инфраструктуры |
| Приватность / GDPR | вычёркивание значения поля с сохранением листа дерева | Удаление и неизменяемость перестают конфликтовать **внутри журнала**; копию в WORM-архиве вычёркивание не достаёт — см. аудит |
| Подключение | один вызов SDK **или** экспортер OpenTelemetry | OTel уже стоит у целевой аудитории |
| Проверка | статический бинарь без зависимостей + один HTML-файл, работающий офлайн в браузере | Юрист оппонента не поставит Python |
| Языки | Python первым, TypeScript вторым, побайтовая идентичность через общие векторы | Универсальность проверяется тестами, а не обещанием |

## 1. Границы первой версии

**Делаем:** библиотека записи, формат, утилита проверки, страница-выписка.

**Не делаем** (подтверждаем список из идеи): веб-интерфейс, облако, аккаунты, биллинг, аналитику качества ответов, метрики, интеграции «со всем подряд».

**Добавляем к списку «не делаем»:** собственную базу данных, свой протокол передачи, свой формат сериализации, свой криптографический примитив. Каждый пункт — источник несовместимости через три года.

## 2. Пять слоёв

```
1. Захват        — перехват события в приложении (SDK / OTel-экспортер)
2. Запись        — отпечаток записи, звено, добавление в цепь, запись на диск
3. Сохранность   — приёмники: локальный каталог, WORM-хранилище клиента
4. Пломба        — суточное дерево, публикация отпечатка вовне
5. Проверка      — сборка пакета доказательства, офлайн-верификация, выписка
```

Слои 1–3 работают у клиента и без сети. Слой 4 требует сети раз в сутки и деградирует мягко. Слой 5 не требует нас вообще — ни сети, ни серверов, ни аккаунта.

Это разделение — не архитектурная эстетика. Оно означает, что отказ нашей стороны не ломает продукт ни в одной точке, кроме свежести пломбы.

## 3. Решение: отпечаток записи считается по дереву полей, а не по всему тексту

Наивный вариант — хешировать сериализованную запись целиком. Отвергнут по двум причинам.

**Причина первая: канонизация.** Если хешируем «объект», то через год другая версия библиотеки переставит ключи, изменит экранирование или точность чисел — и отпечаток перестанет сходиться. Это классическая причина смерти подобных форматов.

**Причина вторая, главная: вычёркивание.** В записях лежат персональные данные. Право на удаление и неизменяемая цепь выглядят как прямое противоречие. Хеш от целого текста делает их действительно несовместимыми: удалил слово — потерял пломбу на всю запись.

**Как делаем.** Запись — набор именованных полей. Для каждого поля берётся отдельная случайная соль в 16 байт. Лист дерева = отпечаток от (имя поля + соль + значение). Листья сортируются по имени, над ними строится двоичное дерево, корень — содержательный отпечаток записи.

Что это даёт:

- **Вычеркнуть поле** — удалить его значение и соль, оставить лист. Отпечаток записи не меняется, цепь продолжает сходиться, содержимое физически отсутствует.
- **Соль обязательна.** Без неё поле со значением «да» или «отказано» подбирается перебором за миллисекунду, и вычёркивание становится декорацией.
- **Показать одно поле, скрыв остальные** — та же механика. Оппоненту можно отдать ответ бота, не отдавая системный промпт и не теряя доказуемости.
- **Само вычёркивание — событие**, которое пишется в цепь новой записью: когда, какое поле, по какому основанию. Пробел перестаёт быть подозрительным, потому что он объяснён и датирован.

Побочный эффект: канонизация больше не нужна. Хешируются точные байты значения, а не результат чьей-то сериализации.

## 4. Решение: цепь внутри потока, дерево над сутками

**Цепь** даёт порядок и отсутствие вставок: каждое звено включает отпечаток предыдущего и свой порядковый номер. Но цепь плоха для показа одной записи — чтобы проверить звено, нужны все предыдущие.

**Дерево** решает это: за отрезок (сутки по умолчанию) строится дерево над отпечатками звеньев, публикуется корень. Доказательство принадлежности одной записи — десяток отпечатков, около килобайта.

Практический смысл: чтобы доказать один разговор из четырёх миллионов, вы отдаёте оппоненту одну запись, а не весь журнал. Это не оптимизация, а требование — отдавать весь журнал юридически неприемлемо.

**Суточные корни тоже связаны в цепь** (каждый включает предыдущий). Иначе можно переписать целые сутки, если пломба за них потерялась.

**Несколько процессов** пишут в разные потоки, каждый со своей цепью. Суточное дерево накрывает все потоки сразу. Это убирает блокировки на горячем пути и делает горизонтальное масштабирование бесплатным.

## 5. Решение: пломба ставится в трёх местах одновременно

Здесь был единственный по-настоящему открытый вопрос. Решение: **не выбирать одно место, потому что аудитории разные, а стоимость каждой пломбы — один отпечаток в 32 байта.**

**1. Штамп времени по RFC 3161, при возможности квалифицированный по eIDAS.**
Для суда и страховщика. Квалифицированный штамп в ЕС имеет установленную законом презумпцию точности времени и целостности — это единственный вариант, который не требует объяснять судье, что такое дерево отпечатков. Проверяется офлайн по сертификату службы.

**2. OpenTimestamps (привязка к Bitcoin).**
Для технического скептика. Никто не контролирует, бесплатно, агрегируется, проверяется офлайн. Аргумент, который закрывает возражение «а вдруг служба штампов с вами в сговоре».

**3. Публичная лента отпечатков** (публичный репозиторий с добавлением в конец).
Для обнаружения раздвоения. Первые две пломбы не мешают недобросовестному оператору вести два журнала и предъявлять удобный. Публичная перечислимая лента мешает: два разных суточных отпечатка от одного потока за одну дату видны любому третьему лицу.

Отказы этих трёх механизмов не коррелируют между собой. Пломба считается поставленной, если сработала хотя бы одна; в выписке честно указывается, какие именно.

Формат описывает пломбу как типизированный блок с подключаемым проверяющим модулем — добавление национальной службы штампов под конкретного заказчика не должно требовать изменения формата.

## 6. Решение: двусторонняя граница времени

Пломба доказывает «не позже». Этого достаточно для главного сценария, но остаётся щель: запись можно изготовить задним числом и запечатать сегодня, утверждая, что она из прошлого года.

**Решение:** в начале каждого отрезка в цепь пишется значение публичного маяка случайности (drand — публичный, проверяется офлайн по открытому ключу сети, не требует регистрации). Значение маяка нельзя было знать заранее. Всё, что стоит в цепи после него, создано после его публикации.

Итог: интервал **[маяк, пломба]**. «Запись сделана не раньше вторника 14:00 и не позже среды 03:00, и с тех пор не изменялась.»

Это ровно та аналогия с лотерейным билетом, которая уже есть в идее, только сделанная буквально. Маяк — это номер тиража, напечатанный на билете.

Деградация: маяк недоступен — пишем отрезок без него, в выписке граница снизу отсутствует. Никаких падений приложения из-за недоступности внешнего сервиса.

## 7. Решение: ключей нет

Целостность не требует секретов — в этом её преимущество перед подписью. У нас нет ключей, у клиента нет ключей, терять нечего, ротировать нечего, скомпрометировать нечего.

**Честная формулировка того, что доказано без подписи:** «это содержимое существовало в этом интервале времени и с тех пор не менялось». Не доказано: «его написала компания X».

Для главного сценария этого хватает: журнал предъявляет сам оператор, авторство он не оспаривает — спор идёт о содержании и дате. Именно дату мы и закрываем.

**Подпись — опция сверху**, для тех, кому нужно связать журнал с организацией: ключ Ed25519 или существующий сертификат организации. Выключена по умолчанию. Проверка пакета без подписи проходит полностью, с подписью — добавляет одну строку в выписку.

## 8. Решение: сохранность — это отдельная работа, а не следствие целостности

Вход на рынок — «записи исчезают через 30 дней». Значит продукт обязан реально решать хранение, а не только подлинность.

- **Формат хранения** — обычные файлы: сегменты по одной записи в строке плюс файлы пломб. Без базы данных. Через семь лет эксперт должен открыть каталог и всё понять без нашей инфраструктуры.
- **Приёмники**: локальный каталог по умолчанию; опционально — хранилище клиента с блокировкой на запись (S3 Object Lock и аналоги). Режим соответствия в таких хранилищах не позволяет удалить объект даже владельцу учётной записи до истечения срока. Это независимое от нас и от клиента принуждение к хранению — самая сильная часть предложения по сохранности.
- **Данные у клиента.** Мы их не храним и не видим. Это следует из позиции «хранить чужие доказательства может только организация с репутацией» и снимает большую часть вопросов безопасности на старте.

## 9. Решение: горячий путь не роняет приложение и не врёт

Требования к записи, в порядке приоритета:

1. **Никогда не терять запись молча.** Очередь ограничена; при переполнении — блокировка с таймаутом, затем явная ошибка. Тихий сброс события для доказательственного продукта недопустим.
2. **Никогда не создавать ложных пробелов.** Порядковый номер присваивается в момент долговечной записи, а не в момент вызова. Иначе падение процесса оставляет дыру в нумерации, неотличимую от подчистки.
3. **Не блокировать вызывающий код.** Запись уходит в очередь, фоновый поток пакетно сбрасывает на диск.
4. **Синхронный режим** — на явно помеченных критичных событиях, где потеря дороже задержки.

Ограничение честное и документированное: между сбросами на диск существует окно потери. Потерянная запись просто отсутствует — она не выглядит как удалённая, но и не доказывает, что её не было. Уменьшается размером окна.

## 10. Решение: подключение через один вызов и через OpenTelemetry

**Прямой вызов SDK** — для тех, кто пишет своё.

**Экспортер OpenTelemetry** — основной путь. У целевой аудитории (разработчики ИИ-агентов, обеспокоенные воспроизводимостью) наблюдаемость уже стоит, и почти вся она построена на OTel. Экспортер означает, что «одна строка кода» — это правда, а не маркетинг, и что мы буквально «работаем рядом» с существующими системами, как и заявлено в идее.

Порядок: Python (язык ИИ-стека), затем TypeScript. Побайтовая идентичность записей между языками проверяется общим набором тестовых векторов — это и есть техническое содержание слова «универсально».

## 11. Решение: три верификатора, и все работают офлайн

Проверка на машине оппонента без обращения к нам — жёсткое требование, а не удобство. Если для проверки нужны мы, доказательство обесценивается наполовину.

1. **Статический бинарь без зависимостей** (Go), одна команда, понятный код возврата — для инженера и для CI.
2. **Один HTML-файл**, открывается в браузере офлайн, файл доказательства перетаскивается мышью — для юриста, аудитора и страховщика. Ничего не устанавливать, никуда не отправлять. Это тот элемент, который решает исход разговора чаще, чем вся остальная криптография.
3. **Библиотека проверки** внутри SDK — для встраивания в чужие процессы.

Пакет доказательства — один файл `.seal`: раскрываемые записи с солями, листья вычеркнутых полей, пути в дереве, суточные отметки, пломбы, свидетельство маяка, страница-выписка и текстовая инструкция обычным языком.

Вывод верификатора — не «OK», а фраза, которую можно вставить в письмо:

> Содержимое совпадает с отпечатком. Отпечаток входит в суточное дерево от 14 марта. Суточный отпечаток запечатан двумя независимыми способами. Запись существовала не позднее 15 марта 03:12 UTC и не ранее 14 марта 09:00 UTC, и с тех пор не изменялась.

## 11а. Решение: как выглядит выписка

Выписка — главный видимый артефакт продукта. Требования к ней вытекают из модели угроз, а не из вкуса.

**Время показывается интервалом, а не точкой.** «Запись сделана в 14:33» — это заявление часов подозреваемой стороны. Показываем отрезок: не раньше маяка, не позже пломбы. Визуально — линия с двумя засечками; словами — «не раньше 12.03 14:30, не позже 13.03 03:12».

**Состояний три, а не два.** Зелёное «запечатано», жёлтое «сходится, пломба будет к 03:00», красное «не совпадает». Жёлтое — самое частое состояние в первые сутки жизни записи; бинарная схема на нём соврёт, а один случай лжи убивает доверие ко всему инструменту.

**Записанное отделено от выведенного.** Блок «что записано» и блок «из записи следует» — разные разделы с явной пометкой. Смешение факта и интерпретации даёт оппоненту возможность оспорить одну неточную формулировку и обесценить весь документ.

**Экран несовпадения не показывает прежний текст.** Мы его не храним — храним только отпечаток. Показывать «было → стало» с подсветкой изменённого слова нельзя: это подразумевает наличие оригинала, которого нет, и первый же грамотный оппонент на этом построит возражение. Верификатор называет запись, оба отпечатка и границу времени и прямо пишет, что прежнее содержимое восстановлению не подлежит.

**Локализация — до записи, но не до поля.** Отпечаток считается по записи целиком, поэтому определить, какое именно поле изменено, по нему невозможно. Показывать имя поля на экране несовпадения — то же самое переоценивание, что и показ прежнего текста. Формулировка «запись seq=3 не совпадает» — предел того, что доказано.

Диаграмма «было → стало» остаётся, но только как объяснение механики на сайте, а не как экран продукта.

**Вычёркивание — строка в хронологии.** Датированная и объяснённая. Объяснённый пробел доказывает добросовестность; необъяснённый выглядит как подчистка.

**Документ двухслойный.** Страница 1 — обычным языком, для юриста и страховщика. Страница 2 — техническое приложение: отпечатки, путь в дереве, пломбы, версия формата, для эксперта оппонента. Без второй страницы первая — просто напечатанный текст.

**Печать важнее экрана.** Документ живёт в письме, в материалах дела и в бумажной папке. Ровно одна страница A4, отдельная печатная тема, каждое состояние обозначено значком и словом, а не только цветом — в чёрно-белой печати цвет пропадает.

**Шапка идентифицирует журнал:** чья установка, какой поток, какой эпизод, идентификатор записи. Иначе документ невозможно сопоставить с исходными данными.

**Проверка — действие, а не сноска.** Кнопка проверки и приложенный пакет стоят в самом заметном блоке страницы. Это единственное, что отличает документ от красиво свёрстанного утверждения.

## 12. Модель угроз: что доказано и что нет

Раздел обязан быть в README на видном месте. Продукт, который переоценивает себя, разваливается при первом квалифицированном возражении.

**Доказываем:**
- содержимое записи не менялось после постановки пломбы;
- запись существовала не позже времени пломбы;
- запись создана не раньше времени маяка;
- записи в потоке идут в этом порядке, без вставок и без изъятий в середине;
- вычеркнутое поле вычеркнуто явно, датировано и объяснено.

**Не доказываем:**
- что запись **правдива** — пломба не знает, что происходило на самом деле;
- что журнал **полон** — то, что вообще не записали, не оставляет следа;
- **авторство** — без опциональной подписи;
- отсутствие обрезки хвоста **между** пломбами — остаточное окно, сокращается частотой пломб и квитанциями контрагенту.

**Что закрыто отдельно:** раздвоение журнала (публичная лента), подбор вычеркнутых значений (соли), подмена формы дерева (разделение доменов при хешировании), доверие часам пишущей стороны (время берётся только из пломбы и маяка, собственная отметка записи — заявление, а не доказательство).

## 13. Дорожная карта

**Этап 0 — спецификация и тестовые векторы. Сделано.**
Формат зафиксирован до первой строки библиотечного кода. [FORMAT.md](FORMAT.md) — нормативная версия 1; [spec/](spec/) — эталонная реализация, девять наборов векторов и конформанс-раннер (111 проверок, включая восемь отрицательных случаев). Сборка векторов вскрыла шесть неоднозначностей, на которых вторая реализация разошлась бы с первой; все устранены и перечислены в разделе 12 спецификации. Пересборка векторов даёт побайтово тот же результат — случайности в наборе нет.

**Этап 1 — Python SDK + проверка. Сделано.**
[python/](python/): запись с фоновым потоком и громким отказом при переполнении, цепь, отрезки, суточное дерево, вычёркивание, три типа пломб, маяк, пакет `.seal`, выписка, команда проверки. 35 тестов, включая побайтовую сверку с векторами этапа 0 и сценарии подделки. Пакет доказательства на одну запись — около 6 КБ.

Уточнено по ходу: закрывать можно только завершившиеся сутки (запечатанный отрезок больше не принимает записи), и локализация расхождения возможна до записи, но не до поля.

**Этап 2 — независимые верификаторы. Сделано.**
[verifier/](verifier/): три независимые реализации проверки.

- `aihash-verify` — статический бинарь на Go, только стандартная библиотека; проверяет и пакет, и журнал целиком; собирается под macOS, Linux и Windows. На Linux — полностью статический файл.
- `verify.html` — один файл, открывается двойным щелчком с диска, работает офлайн; для юриста, аудитора и страховщика.
- `aihash-verify.js` — та же проверка через node, для окружений, где Go нет.

Каждая сверена с векторами этапа 0 отдельно, плюс перекрёстный тест гоняет все три по одним и тем же пакетам и требует совпадения вердикта — на исправном, на подделанном и на порванной ленте.

Ради этого пакет `.seal` переведён на хранение без сжатия (верификатору на JS не нужен распаковщик), а SHA-256 в браузерной версии написан в самом файле, потому что `crypto.subtle` доступен не во всех браузерах при открытии с диска.

Уточнено по ходу: верификатор, приложенный к пакету стороной спора, не является независимой проверкой — страница, `VERIFY.txt` и сборка бинарей говорят это сами и печатают отпечатки для сверки.

**Этап 3 — сохранность и OTel. Сделано.**
Экспортер OpenTelemetry (`aihash.otel.install` в одну строку): завершённый span становится записью, атрибуты `gen_ai.*` и ресурс сохраняются, исключения записываются, вложенность трассы восстанавливается. Чужой атрибут не может подменить наши поля или влезть в зарезервированные имена — это сделало бы запись недостоверной.

Приёмники сохранности: `local:` (снимает право на запись) и `s3://` (Object Lock, режим COMPLIANCE). Политика хранения с отсчётом срока от самих суток, а не от момента архивации. Команда `aihash retention` отвечает цифрами на главное сообщение продажи и возвращает ненулевой код, когда есть пробел.

**Архив — сам по себе валидный журнал**, поэтому его проверяет тот же верификатор без единой правки, включая бинарь на Go. Это решение важнее, чем кажется: доказательства, которые нельзя проверить в месте хранения, — половина доказательства.

Уточнено по ходу: приёмник S3 обязан отказываться писать в корзину без включённого Object Lock. Худший исход — клиент считает себя защищённым, не будучи защищённым, и узнаёт об этом в день претензии.

Граница честности: тесты доказывают, что мы запрашиваем верный режим и срок; что блокировка работает — поведение AWS, локальным макетом это не проверяется.

**Этап 4 — TypeScript SDK. Сделано.**
[typescript/](typescript/): запись, цепь, вычёркивание, отрезки, суточное дерево, пломба `feed`, пакет `.seal`, выписка, проверка и командная строка. Ни одной зависимости во время работы — только стандартная библиотека Node.

Успех этапа был определён заранее и достигнут: ядро сходится с векторами этапа 0 побайтово. Сверх того проверено большее — журнал, написанный TypeScript, принимают Python и бинарь на Go; журнал, написанный Python, принимает TypeScript; подделку в пакете из TypeScript ловят все три. Формат один, значит и журналы взаимозаменяемы, а не только числа в тестах.

Найдено по ходу и исправлено в обеих реализациях:
- **Дописывание в запечатанный отрезок.** Пломбу ставит отдельный процесс по расписанию, поэтому отрезок может быть запечатан, пока долгоживущий писатель держит его открытым. Проверка была только при смене суток — теперь на каждой записи. Дефект был и в Python.
- **Гонка в охране очереди** (только TypeScript): между проверкой места и постановкой в очередь был `await`, и сотня одновременных вызовов проскакивала охрану целиком.
- **Ошибка внутри потока записи убивала цикл** (только Python): синхронный вызывающий висел до таймаута и получал невнятное «не подтверждена» вместо причины. Теперь некорректный вызов отклоняется сразу и поток продолжает работать; отказ ввода-вывода по-прежнему останавливает всё.

Не портировано намеренно: штампы RFC 3161 и OpenTimestamps (требуют разбора CMS — сторонняя зависимость в SDK без зависимостей неуместна) и приёмники сохранности (операционная задача рядом с `seal`, а S3 потребовал бы `aws-sdk`).

**Живой прогон перед публикацией. Сделано.**
Всё предыдущее было синтетикой: выдуманные эпизоды, без сети, только самая слабая пломба `feed`. Прогон против настоящих служб — маяк drand и служба штампов времени freetsa.org — дал настоящую двустороннюю границу шириной 31 секунда и вскрыл три дефекта, которых не могли поймать никакие синтетические тесты.

1. **Верификатор ложно обвинял исправный штамп.** Принадлежность штампа отметке проверялась разбором текстового вывода `openssl ts -reply -text`, а тот печатает дамп с отступами и ASCII-колонкой, а не сплошной hex. Отметка не находилась никогда. Ложное обвинение — худший отказ, какой этот продукт может выдать: он превращает инструмент защиты в оружие против собственного владельца. Исправлено проверкой сырых байтов DER; настоящий ответ службы уложен в [spec/fixtures/rfc3161/](spec/fixtures/rfc3161/) и закрыт тестами во всех четырёх реализациях.
2. **Браузерное ядро вообще не проверяло принадлежность штампа** — молча считало его непроверяемым. Теперь проверяет.
3. **Сертификата службы не было в пакете**, поэтому подпись штампа офлайн проверить было нельзя — прямое противоречие требованию «проверка работает без сети». Теперь сертификат едет в `certs/` **вне** `anchors/`, но подпись, сошедшаяся с приложенным сертификатом, объявляется НЕ проверенной: сертификат приложила сторона спора, и подделав и штамп, и корень, такую проверку пройти можно. Верификатор печатает отпечаток сертификата, чтобы сверка с независимо полученным заняла одну команду.

Измерено на объёме 50 000 записей: запись 36 600 записей/с, 600 байт на запись, закрытие суток 0,65 с, проверка журнала 75 000 записей/с (бинарь — 0,25 с на весь журнал). Доказательство одной записи из 50 000 — 16 шагов в дереве, 13,7 КБ вместе с выпиской. Рост логарифмический, как и задумано.

Не проверено вживую: OpenTimestamps (публикует в общедоступные календари необратимо), принуждение S3 Object Lock (нужен настоящий AWS), поток от настоящей языковой модели.

Отдельная эксплуатационная находка: на сборке python.org для macOS отсутствуют корневые сертификаты, и пломба RFC 3161 не ставится. Отказ громкий и виден в выводе `seal`, но об этом надо написать в документации.

**Аудит перед публикацией. Сделано.**
Полный разбор кодовой базы с трассировкой каждого сценария. Найдено и исправлено: обход каталога через `stream_id`, потеря записей при вычёркивании, гонка при открытии потока в TypeScript, битые пути в опубликованном пакете npm, отсутствие пределов разбора у всех четырёх верификаторов, падение вместо вердикта на кривом пакете, чтение всей истории при каждом запуске процесса и — дважды — ложное обвинение исправного журнала.

Отдельно вскрыто противоречие между вычёркиванием и неизменяемым хранением: удаление персональных данных не достигает архива в режиме `COMPLIANCE` и не может достичь его по построению. Команда предупреждает и возвращает ненулевой код; правильное решение — шифрование значений ключами вне архива — отложено до версии 2 формата.

**Третье состояние пломбы в выводе. Сделано.**
Верификатор говорил «не запечатано» там, где пломба стоит и относится именно к этой суточной отметке, — не сверена была только подпись, потому что нет корневого сертификата службы. Го и браузерное ядро подпись RFC 3161 не проверяют вовсе, поэтому для них это был единственный достижимый исход на любом журнале с настоящим штампом.

Недоговорка того же сорта, что ложное обвинение, только в другую сторону: получатель решает, что журнал не запечатан, и недооценивает доказательство. Все четыре реализации теперь различают три случая: пломба проверена; пломба стоит, но подтвердить её здесь нечем; пломбы нет.

Решение по существу: признак «пломба поставлена» отделён от признака «пломбу удалось проверить», и планка первого — **доказанная принадлежность отметке**, а не наличие подходяще названного файла в `anchors/`. Иначе любой файл, положенный туда, смягчал бы вердикт; первая версия правки именно это и делала, и была поймана существующим тестом.

Формат не менялся: `FORMAT.md` уже требовал этого различения (раздел 7.1) — правился код, а не документ. Векторы пересобираются побайтово.

**Дальше — пауза.** Ничего не добавляем, пока не появится посторонний человек с реальным сценарием. Признак успеха и признак провала взяты из идеи без изменений: issue с чужим сценарием — хорошо; сто звёзд и ноль issue — плохо.

## 14. Что делает продукт не просто правильным

Пять мест, где решение заметно лучше ожидаемого:

1. **Двусторонняя граница времени.** Обычно такие системы доказывают только «не позже». Маяк добавляет «не раньше» почти бесплатно и делает объяснение продукта наглядным.
2. **Вычёркивание без потери пломбы.** Право на удаление и неизменяемость обычно подаются как непримиримое противоречие. Здесь они сосуществуют, и это редкий по силе аргумент в европейском разговоре.
3. **Верификатор в браузере.** Оппонент проверяет доказательство перетаскиванием файла, без установки чего-либо и без сети.
4. **Ноль ключей, ноль аккаунтов, ноль наших серверов** на пути проверки.
5. **Одна страница обычным языком** на выходе — то, что реально читает человек, принимающий решение.
