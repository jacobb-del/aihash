# Состояние проекта

Передаточный документ. Читается за пять минут, предполагает, что проект вы не видели.

Дата: 30 июля 2026. Формат `aihash/1` зафиксирован. Все проверки зелёные.

---

## 0. Что это

Журнал работы ИИ-системы, который **нельзя незаметно изменить задним числом**. Не мониторинг: мониторинг отвечает «что происходило», этот продукт отвечает «докажи».

Механика: у каждого поля записи свой отпечаток (SHA-256 от имени, соли и значения) → листья собираются в дерево → его корень есть отпечаток записи → записи связаны в цепь → цепь за сутки сворачивается в дерево → на суточный корень ставится **пломба** у третьей стороны (штамп времени RFC 3161, OpenTimestamps, публичная лента).

Замысел и обоснования решений — в [PRODUCT_IDEA.md](PRODUCT_IDEA.md) и [PLAN.md](PLAN.md). Читать их **до** правок кода: почти каждое неочевидное решение там объяснено, и большинство «улучшений» уже отвергнуты с указанием причины.

## 2. Что сделано и работает

Пять этапов из плана закрыты, плюс аудит перед публикацией.

- **Формат** зафиксирован до кода. Сборка векторов вскрыла 6 неоднозначностей, включая настоящую дыру: отметки склеивали строки без префиксов длины, из-за чего `stream_id="ab"+period="c"` и `"a"+"bc"` давали один отпечаток.
- **Четыре реализации** формата: Python, TypeScript, Go, браузерное ядро. Сходятся с общими векторами побайтово и друг с другом: журнал, написанный одной, принимают остальные.
- **Двусторонняя граница времени.** Маяк drand даёт «не раньше», штамп — «не позже». На живом прогоне интервал вышел шириной **31 секунда**.
- **Вычёркивание не ломает пломбу.** Удаляются значение и соль, лист дерева остаётся: отпечаток записи не меняется. Проверено вживую — персональные данные исчезают с диска, `verify` возвращает 0.
- **Сохранность:** приёмники `local:` и `s3://` с Object Lock, политика хранения, отчёт о пробелах. Архив сам по себе валидный журнал — проверяется тем же бинарём.
- **OpenTelemetry:** `aihash.otel.install(...)` в одну строку.

Измерено на 50 000 записей: запись 36 600 записей/с, 600 байт на запись, закрытие суток 0,65 с, проверка журнала бинарём 0,25 с. Доказательство одной записи из 50 000 — 16 шагов в дереве, 13,7 КБ.

### Как прогнать всё

```bash
python3 verifier/build.py                 # страница-верификатор (нужна первой)
python3 spec/tools/buildtrust.py          # набор корней служб штампов
sh verifier/go/build.sh                   # бинарь
cd typescript && npm install && npx tsc   # SDK на TS

python3 spec/tools/check.py               # 111 проверок векторов
go test -C verifier/go ./...              # Go
node verifier/tests/conformance.js        # 104 проверки браузерного ядра
cd python && .venv/bin/python -m pytest -q # 125 тестов
cd typescript && npm test                 # 37 тестов + сверка четырёх реализаций
```

Порядок важен: `verifier/build.py` кладёт `python/aihash/assets/verify.html`, который вкладывается в каждый пакет `.seal`. Без него пакет собирается, но получателю придётся искать верификатор самому (команда предупредит).

## 3. Что проверено и как

### Восемь атак — `python/tests/test_tampering.py`

Каждый тест: собрать журнал из 10 записей → убедиться, что **неизменённый** принимается → сломать одним способом → убедиться, что порча **состоялась** → потребовать отказа от **всех** реализаций.

| № | Атака | Чем ловится |
|---|---|---|
| 1 | изменён один символ в записи №5 | звено `seq=5` |
| 2 | запись №5 удалена | пропуск в цепи |
| 3 | дописана **правильно сцепленная** запись после пломбы | отметка отрезка (`count`, `last_seq` запечатаны) |
| 4 | записи №3 и №7 переставлены | звено `seq=3` |
| 5 | цепь пересчитана целиком с новым содержимым | **пломба** |
| 6 | файл пломбы удалён | «не подтверждено», **не** «ОК» |
| 6b | пакет без пломбы | код возврата **3**, не 0 |
| 7 | подставлен штамп от другого дня | «поставлен не на эту отметку» |
| 7b | в ленте опубликована другая отметка за эти сутки | отказ |
| 7c | две отметки за одни сутки | раздвоение журнала |
| 8 | изменена **только** метка времени | звено `seq=5` — время связано цепью |
| 9 | подделка внутри пакета (записи, отрезок, сутки) | ×3 |

Плюс контрольные: неизменённый журнал принимают все; все реализации действительно запускаются.

**Проверка, что набор не проходит впустую.** Внёс правдоподобную «оптимизацию» — верификатор доверяет записанному звену вместо пересчёта. Упали ровно 3 теста (1, 4, 8) — те, которые эта ошибка и должна пропускать. После восстановления 16 из 16.

### Какие пломбы были настоящими, какие внутренними

Это важно и легко перепутать.

| Тест | Пломба |
|---|---|
| Атаки 1–6, 7b, 7c, 8, 9 (`test_tampering.py`) | **внутренняя `feed`** — наш собственный код |
| Атака 7 (`test_tampering.py`) | **настоящий** ответ freetsa.org, записанный на диск и воспроизводимый офлайн |
| `test_rfc3161.py`, `rfc3161_test.go`, `rfc3161.test.ts` | **настоящий** ответ службы, фикстура |
| `test_anchor_load_bearing.py` | **настоящий** штамп, и ничего кроме него |

**Моков сети в проекте один** — `moto.mock_aws` для S3 в `test_sinks.py`. Служба штампов **не мокается нигде**: либо настоящий записанный ответ, либо живой запрос по `AIHASH_LIVE_TSA=1`.

### Ручная проверка через openssl

Прогонялась дважды, оба раза чужим инструментом, без нашего кода.

**На файле лога** (`day.jsonl`, 4418 байт, 10 записей):

```
openssl ts -query -data day.jsonl -no_nonce -sha256 -cert -out day.tsq
curl -H "Content-Type: application/timestamp-query" --data-binary @day.tsq \
     https://freetsa.org/tsr -o day.tsr
curl -O https://freetsa.org/files/cacert.pem      # wget на машине нет
openssl ts -verify -data day.jsonl -in day.tsr -CAfile cacert.pem
→ Verification: OK
```

После замены одного символа (`sha256` файла `fe70d538…` → `1ff590cb…`):

```
→ error: ts_check_imprints: message imprint mismatch
→ Verification: FAILED
```

**На суточной отметке** — см. раздел 4.

## 4. Якорь третьей стороны: ДОКАЗАНО, что несущий

Это был главный открытый вопрос проекта. **Он закрыт 30 июля.** Раздел оставлен подробным, потому что это самое важное свойство продукта и его надо уметь перепроверить.

### Что было опасение

Атаки 1–6 опирались на пломбу `feed` — **наш собственный код**. Формально это значило: если бы вся логика ленты была ошибочна, тесты бы этого не заметили, и «защита» сводилась бы к проверке нашего кода нашим же кодом. Про атаку 5 в комментарии было написано «доказывает, что пломба несущая» — это было **преувеличением**, потому что ловила её наша лента.

### Что сделано

`python/tests/test_anchor_load_bearing.py` + фикстура `spec/fixtures/sealed-journal/`.

Журнал из 10 записей, запечатанный **настоящим** штампом freetsa.org (`Jul 30 09:45:37 2026 GMT`, суточная отметка `fef45030…`). Внутренней пломбы `feed` в фикстуре нет вовсе.

Доказательство из трёх частей, и каждая нужна:

1. **Положительный путь** — журнал и штамп сходятся, статус `SEALED`, подпись службы сверена по её корневому сертификату.
2. **Контроль** — журнал пересоздаётся заново с другим содержимым: переписаны все 10 записей, пересчитаны отпечатки полей, звенья, корень отрезка, отметка отрезка и суточная отметка. **Без штампа такая подделка проходит проверку**: `Цепь сходится на всём протяжении`, `rc=0`, у всех реализаций. Без этой части тест не отличал бы «поймал штамп» от «поймала цепь».
3. **Отрицательный путь** — со штампом та же подделка отвергается:

```
НЕ СХОДИТСЯ
  сутки 2026-07-29: пломба rfc3161 не сходится — штамп поставлен не на эту суточную отметку
rc=1
```

Отметка сместилась `fef45030…` → `a4694d1a…`. Go и TypeScript дают то же, `rc=1`.

И то же самое **без нашего кода вообще**:

```
openssl ts -verify -digest a4694d1a… -in day.tsr -CAfile cacert.pem
→ Verification: FAILED   (imprint mismatch)

openssl ts -verify -digest fef45030… -in day.tsr -CAfile cacert.pem
→ Verification: OK
```

Штамп заверяет прежнюю отметку и отказывается заверять новую.

**Вывод: внешний якорь несущий.** Подделку, которую не поймала ни одна наша проверка, поймал штамп службы, и независимый инструмент это подтвердил.

Плюс живой путь `test_live_round_trip_against_the_authority` — настоящий запрос к службе, включается `AIHASH_LIVE_TSA=1`. Прогонялся, проходит. По умолчанию выключен: CI не должен зависеть от чужого сервиса, а фикстура даёт то же покрытие офлайн.

### Что осталось от этого вопроса

Атаки 1–6, 7b, 7c, 8, 9 в `test_tampering.py` **по-прежнему используют только `feed`**. Теперь это не пробел в доказательстве — несущность якоря доказана отдельно, — но усиление возможно и стоит недорого: параметризовать заготовку `sealed` по типу пломбы и прогнать те же атаки против фикстуры с настоящим штампом. Это не приоритет.

## 5. Известные ограничения

Каждое из них продукт называет сам, в выводе команд или в документации. Формулировки не смягчать: переоценивание здесь дороже недосказанности.

**Вычёркивание не достигает WORM-архива.** Две возможности продукта противоречат друг другу: в режиме S3 `COMPLIANCE` прежнюю версию не удалит никто до истечения срока — по построению. `aihash redact` обнаруживает уложенные сутки, называет приёмники и возвращает ненулевой код, когда удаление невозможно. Правильное решение — шифрование значений полей ключами вне архива (удаление ключа = невосстановимость) — это версия 2 формата.

**Локализация расхождения — до записи, но не до поля.** Отпечаток считается по записи целиком. Показывать имя поля нельзя — это переоценивание.

**Прежнее содержимое не восстанавливается.** Хранится только отпечаток. Экран «было → стало» невозможен и в продукте запрещён (осталась только объяснялка для сайта).

**Публичная лента защищает от раздвоения только будучи опубликованной вовне.** По умолчанию лежит внутри журнала, то есть под контролем той же стороны; верификатор говорит это прямым текстом.

**Подпись штампа проверяет только Python.** Корни вшиты (раздел 7), но разбора CMS нет ни в Go, ни в TypeScript, ни в браузере — там штамп остаётся «поставлен, не подтверждён». Это первое действие следующей сессии.

**Принуждение S3 Object Lock обеспечивает AWS, а не библиотека.** Тесты доказывают, что мы запрашиваем `COMPLIANCE` с верной датой и отказываемся писать в корзину без блокировки. Что блокировка работает — не проверено: `moto` режим запоминает, но удаление пропускает.

**На сборке python.org для macOS нет корневых сертификатов** — маяк и штамп не получатся без `SSL_CERT_FILE`. Отказ громкий, виден в выводе `seal`.

**Память при проверке** растёт линейно от размера отрезка: корень дерева требует всех листьев. На 50 тыс. записей в сутки это десятки мегабайт.

**Сертификаты живут меньше, чем обещание проверяемости.** Через 5–10 лет подпись штампа перестанет сверяться из-за истечения срока — не потому, что штамп плох. Продукт в этой ситуации не лжёт (говорит «не подтверждена», а не «подделка»), но и не решает её. Подробно, с опытом и вариантами решения, — раздел 9.

### Решено не делать

- **Веб-интерфейс, облако, аккаунты, биллинг, аналитика качества ответов, метрики** — исходный список границ из идеи, подтверждён.
- **Своя база данных, свой протокол, свой формат сериализации, свой криптографический примитив** — каждый пункт источник несовместимости через три года.
- **Ключи и подписи по умолчанию.** Целостность их не требует, управление ключами убивает такие проекты. Подпись — опция сверху, выключена.
- **Штампы RFC 3161 и OpenTimestamps в TypeScript.** Полноценная проверка требует разбора CMS — сторонняя зависимость в SDK без зависимостей неуместна. Ставятся Python-командой, проверяются бинарём.
- **Приёмники сохранности в TypeScript.** Операционная задача рядом с `seal`; S3 потребовал бы `aws-sdk`.
- **Разбор каталога журнала в браузерном ядре.** Раздуло бы `verify.html`, который обязан оставаться читаемым целиком.
- **Дублирование верификаторов, которое остаётся сознательно.** Выписка существует в двух реализациях (Python и TypeScript) — риск расхождения принят, обе покрыты тестами на обязательные оговорки.

### Не проверено вживую

- **OpenTimestamps** — публикует отпечаток в общедоступные календари необратимо. Требует решения владельца.
- **Принуждение S3 Object Lock** — нужны настоящие ключи AWS.
- **Поток от настоящей языковой модели** — экспортер OTel проверен на настоящем OTel-стеке, но спаны порождены тестом.
- **Внешний криптографический ревью формата.** Всё проверялось автором. Для продукта, чья ценность целиком в доказательности, это не то же самое, что независимый разбор.

## 6. Сделано 30 июля: третье состояние пломбы в выводе

Прежнее «первое действие» закрыто. Верификатор больше не говорит «не запечатано» там, где пломба стоит.

**Что было.** `aihash verify <журнал>` без `--tsa-ca` на журнале с настоящим штампом печатал «Не запечатано суток: 1». Сутки при этом запечатаны, штамп относится именно к этой отметке — не сверена только подпись. Го и TypeScript подпись RFC 3161 не проверяют **вовсе** (разбора CMS там нет и не будет), поэтому для них это был не редкий случай, а единственный достижимый исход на любом журнале с настоящим штампом.

**Что сделано.** В выводе всех **четырёх** реализаций различаются три случая: пломба проверена; пломба стоит, но подтвердить её здесь нечем; пломбы нет. Формат не тронут — векторы пересобираются побайтово, `FORMAT.md` не правился: документ был прав, код ему не соответствовал.

Механика распознавания вынесена в признак `placed` на результате проверки пломбы: **установлено ли, что пломба поставлена именно на эту отметку**, — отдельно от вопроса «удалось ли её проверить». Планка намеренно высокая: `placed` ставится там, где принадлежность доказана (сырые байты штампа сошлись с отметкой; запись найдена в ленте; ответ ots разобран клиентом), и **не** ставится там, где в `anchors/` просто лежит подходяще названный файл. Первая версия правки этого не различала, и нераспознанный файл в каталоге смягчал вердикт — переоценивание, поймано существующим тестом.

Тронуто: `anchors.py`, `verify.py`, `cli.py`, `verifier/go/verify.go`, `verifier/go/main.go`, `typescript/src/{seal,verify,cli}.ts`, `verifier/src/verifier.js`, `verifier/src/verify.html.tmpl`, обёртка CLI в `verifier/build.py`. `report.html` правки не потребовал: он ветвится по факту наличия файлов пломб, а не по исходу проверки.

Коды возврата **не менялись**: пакет без подтверждённой пломбы по-прежнему даёт 3, журнал — 0. Код 3 объединяет «пломбы нет» и «пломба не подтверждена» намеренно; словами их различать обязательно.

Заодно починен `npm test`: скрипт передавал `node --test` каталог, а Node 24 пытается загрузить такой путь как модуль. Теперь шаблон `dist/test/*.test.js`.

**Чем закрыто.** Два новых теста в `test_anchor_load_bearing.py`, зеркальных друг другу: `test_stamp_without_ca_is_unconfirmed_not_unsealed` (не занижать) и `test_journal_without_any_anchor_still_says_unsealed` (не завышать). Оба гоняют и Го, и TypeScript. Вторая нужна ровно затем, чтобы первую нельзя было удовлетворить, убрав слова «не запечатано» отовсюду.

Проверено мутациями, что тесты не проходят впустую:

| Нарочная поломка | Упало |
|---|---|
| `placed` всегда «да» | `..._without_any_anchor_still_says_unsealed`, `..._flawless_without_the_stamp` |
| `placed` всегда «нет» | `..._without_ca_is_unconfirmed_not_unsealed` |
| день всегда «запечатан» | обе новые + атаки 6 и 6b |
| штамп принимается без сверки отпечатка | `..._caught_by_the_stamp_alone`, атака 7 |

## 7. Сделано 30 июля: корень доверия переехал в верификатор

**Дыра.** Сертификат службы штампов ехал вместе с пакетом. Подделыватель, приложивший к своему штампу свой корень, заверял сам себя — пакет удостоверял собственную подлинность. Смягчение было («подпись, сошедшаяся с приложенным сертификатом, объявляется непроверенной»), но сам приложенный файл всё равно использовался как `-CAfile`, а это уже построение доверия на материале стороны спора.

Вторая половина той же проблемы: без `--tsa-ca` получатель не мог подтвердить ничего, и исправный журнал в норме выглядел неподтверждённым. Обещание «одна команда» не выполнялось.

**Решение — как у браузеров: корни едут с верификатором.**

```
spec/trust/roots.json      источник истины: версия набора, происхождение каждого корня
spec/tools/trust.py        чтение и сверка отпечатков
spec/tools/buildtrust.py   раскладка по реализациям
python/aihash/trust.py     загрузка вшитого набора с пересчётом отпечатков
python/aihash/assets/trust.json   вшитая копия (коммитится, см. ниже)
```

Правила, которые здесь важнее кода:

- **Ни сертификат из пакета, ни корень, вложенный в сам штамп, не создают доверия.** Оба приехали с уликой. Служат ровно одному: назвать получателю, какой корень искать. Штамп FreeTSA везёт свой корень внутри себя — поэтому мало игнорировать `certs/` в пакете.
- **`--tsa-ca` главнее набора.** Службу, до которой наш выпуск не дошёл, обязано быть можно проверить сразу.
- **Отпечатки пересчитываются при каждой загрузке.** Набор с непроверенным корнем хуже отсутствующего: он создаёт видимость доверия.
- **Вердикт называет версию набора и сработавший корень.** Оспорить сам набор — законный ход стороны спора, и ей должно быть, что оспаривать.
- **Набор коммитится, хотя лежит в собираемом каталоге.** `.gitignore` правился специально: подмена корня обязана быть видна в обзоре кода и в истории.

**Что чем отвечает.** Три исхода и ровно одна граница, за которой начинается обвинение:

| Ситуация | Ответ |
|---|---|
| корень из набора подошёл | запечатано, `rc=0` |
| службы нет в наборе | «пломба стоит, не подтверждена», `rc=3`, с указанием нужного корня по отпечатку |
| цепь не собралась по любой причине | то же самое, `rc=3` |
| **корень назвался известной службой, но это другой ключ** | **`rc=1`** — выдача себя за чужую службу |
| отпечаток штампа не тот | `rc=1` — единственная проверка, где мы читаем сырые байты сами |

Почему неизвестная служба — это `rc=3`, а не `rc=1`: добросовестный пользователь такой службы и подделыватель для нас неразличимы, и клеймить обоих дороже, чем пропустить. Подделку поймает суд; компания, которой инструмент солгал на честной записи, его больше не запустит.

**Чем закрыто.** `python/tests/faketsa.py` поднимает **настоящую поддельную службу штампов**: свой удостоверяющий центр, свой сертификат подписанта с `timeStamping`, свой штамп. Полученный `.tsr` криптографически безупречен — `openssl ts -verify` принимает его без замечаний, если дать ему корень этого центра. Слабая подделка ничего бы не проверяла.

- `test_forged_stamp_with_its_own_root_in_the_bundle_is_not_accepted` — переписанный журнал + поддельный штамп + поддельный корень в пакете. Не проходит (`rc=3`). **Контроль:** тот же пакет с `--tsa-ca` поддельного корня проходит — значит разница ровно в том, откуда пришло доверие, а не в чём-то ещё.
- `test_root_impersonating_a_known_authority_is_an_accusation` — тонкий и легко теряемый при рефакторинге случай.
- `test_trust_store.py` — целостность набора, происхождение каждого корня, расхождение вшитой копии с `spec/trust`.

Проверено мутациями, что тесты не проходят впустую:

| Нарочная поломка | Упало |
|---|---|
| сертификат из пакета снова строит доверие | `..._own_root_in_the_bundle_is_not_accepted` |
| набор не пересчитывает отпечатки | `test_tampered_root_is_rejected_not_used` |
| проверка подмены известного корня выключена | `..._impersonating_a_known_authority...` |
| подпись объявляется проверенной без сверки цепи | 5 тестов в трёх файлах |

**Что изменилось в поведении** (важно при чтении старых тестов): два теста в `test_rfc3161.py` переписаны. Первый требовал «без сертификата — не подтверждена»; теперь набор её подтверждает, и тест переехал на службу вне набора. Второй требовал `rc=1`, когда цепь не собралась; теперь это `rc=3` по решению выше.

**Остаточный риск, записан осознанно.** Перевыпуск корня той же службой с тем же именем и **новым** ключом выглядит для проверки на подмену так же, как выдача себя за неё, — и будет обвинён. Перевыпуск с прежним ключом (продление срока) не обвиняется: сравнение идёт по ключу, а не по отпечатку. Более точного различения без внешнего источника не существует.

**В наборе один корень — FreeTSA.** Единственный, который проверяется офлайн работающей фикстурой. DigiCert, Sectigo и квалифицированные TSA ЕС требуют загрузки из сети и, главное, критерия попадания в набор: вшивая корни, мы заводим собственную программу доверия без политики, тогда как у браузеров на это есть CA/B Forum. Манифест объявляет критерий прямым текстом, а процедура добавления описана — дописать корень будет механической работой.

## 9. Открытая проблема: сертификаты живут меньше, чем обещание

Продукт обещает проверяемость через 5–10 лет. Сертификаты столько не живут. Раздел записан, **ничего не реализовано** — решение требует выбора владельца.

### Суть

Штамп RFC 3161 подписан сертификатом службы, у которого есть срок. Когда он истекает, штамп не становится ложным — он остаётся ровно тем же набором байтов, — но обычная проверка цепи строится **на текущий момент** и отказывает.

Это не предположение. Опыт: поднята служба штампов, сертификат подписанта выписан со сроком 2024‑01‑01 … 2025‑01‑01, штамп поставлен сегодня.

```
openssl ts -verify -digest <отметка> -in r.tsr -CAfile ca.crt
→ Verify error:certificate has expired
→ Verification: FAILED
```

Штамп безупречен, отпечаток на месте, ключ не скомпрометирован — и всё равно FAILED.

### Что увидит получатель в 2033-м

Проверено на том же материале нашим верификатором:

```
статус: unverified | пломба поставлена: True
вердикт: «пломба стоит, но здесь не подтверждена», rc=3
```

**Не обвинение.** Принадлежность штампа отметке проверяется по сырым байтам и от сроков не зависит вовсе, поэтому «пломба поставлена» остаётся истиной; отказывает только сверка подписи, а любой её отказ мы объявляем неподтверждённостью, а не подделкой.

Это прямое следствие решения, принятого сегодня в разделе 7. **До него исход был бы `rc=1`** — то есть в день, когда служба меняет сертификат, весь архив честных журналов разом объявляется поддельным. Решение принималось из общего правила («добросовестный пользователь неизвестной службы и подделыватель неразличимы»), а сработало здесь, где цена ошибки максимальна.

### Горизонт

| Что | До какого числа |
|---|---|
| Сертификат подписанта FreeTSA | 2 февраля 2040 |
| Корень FreeTSA (в нашем наборе) | 7 марта 2041 |

Для нынешней фикстуры 2033 год безопасен. Но у квалифицированных служб ЕС сертификат подписанта обычно живёт 3–5 лет, а не четырнадцать, — там проблема наступит гораздо раньше, и именно на тех штампах, ради которых квалифицированная служба и берётся.

### Решения, между которыми выбирать

**1. Проверять цепь на момент штампа, а не на текущий.** Самое дешёвое и закрывает ровно истечение срока. В Go это `x509.VerifyOptions.CurrentTime`; `openssl ts -verify` так не умеет вовсе — значит для Python нужен либо свой разбор, либо отказ от openssl. Не закрывает **отзыв**: сертификат, отозванный до истечения, так и останется невидимым, а отличить «был действителен тогда» от «был отозван тогда» без сохранённых сведений о статусе невозможно.

**2. Хранить полное свидетельство на момент штампа.** Цепь сертификатов целиком плюс ответы CRL/OCSP, полученные тогда же, укладываются в пакет как часть доказательства. Это то, что стандарты называют долгосрочной проверяемостью (RFC 5126, ETSI). Дороже: растёт размер пакета, появляется работа в момент постановки пломбы, а не в момент проверки. Зато проверка остаётся полностью офлайн и через двадцать лет.

**3. Переподписывание архива, пока старые сертификаты действительны.** Поверх старого штампа периодически ставится новый, более свежей службой: пока цепочка переподписей не прервана, доказательство живёт неограниченно (схема записей-свидетельств, RFC 4998). Самое сильное и самое дорогое: требует календаря, процесса и того, чтобы кто-то за этим следил все десять лет. Ошибка здесь тихая — пропущенный срок обнаружится в день спора.

### Почему отложено

Продукт не имеет ни одного постороннего пользователя. Все три решения — это работа на десятилетний горизонт, а до первого чужого сценария неизвестно даже, какая служба штампов и какая юрисдикция окажутся нужны: от этого зависит и срок жизни сертификатов, и то, обязательна ли долгосрочная проверяемость по регламенту. Ближайшая реальная дата — 2040 год.

Обязательное условие отсрочки уже выполнено: продукт **не лжёт** в этой ситуации, а честно говорит «не подтверждена» и называет, чего не хватает. Отложена оптимизация, а не корректность.

### Известное ограничение: сообщение врёт про причину. Горизонт 2040. **Не чинить**

Когда цепь не собирается по любой причине, сообщение гласит «его службы нет в наборе корней». Для истёкшего сертификата **известной** службы это неправда: корень в наборе есть, отказала проверка срока. В 2041 году верификатор скажет про FreeTSA «службы нет в наборе» и отправит получателя искать сертификат, который у него уже лежит.

Отдельно: строка `подпись не сошлась с переопределение --tsa-ca` не согласована по падежу.

**Решение принято: не трогать.** Дефект срабатывает только тогда, когда у известной службы истёк сертификат, а у FreeTSA это 2040 год. Сегодня он не влияет ни на кого. Правка невелика — различать «корень не найден» и «корень найден, цепь не собралась», — но делается она вместе с решением выше, а не до него и не отдельно.

## 10. Сделано 30 июля: репозиторий готов к публикации

Последний незакрытый пункт чеклиста — «чужой человек проверил и понял вывод» — кодом не закрывается. Закрывается самообслуживанием: человек скачивает репозиторий и убеждается сам, ничего не спрашивая.

**Публичный пример — [demo/](demo/README.md).** Настоящий журнал с настоящим штампом freetsa.org, готовый пакет `episode.seal`, верификатор одним файлом. Две команды: `pip install ./python`, `aihash verify ./demo/journal` → `Запечатано`. Потом человек меняет **один символ** в записи и получает `НЕ СХОДИТСЯ ... seq=3` и код 1. Плюс путь через `openssl` вообще без нашего кода.

Проверено дословно на чистом клоне в чистом контейнере: обе команды работают, вывод совпадает с обещанным в README посимвольно.

**Гифка `demo/aihash.gif`** — первый экран README. 16 секунд, 57 КБ. Собрана скриптом, который прогоняет сценарий и рисует кадры **из захваченного вывода**: ни одна строка не набрана руками. Если верификатор изменит формулировку, гифку надо пересобрать — она перестанет соответствовать выводу, а не наоборот.

### Два дефекта чистоты, найденные при подготовке

**1. Весь `demo/` лежал в `.gitignore`.** README обещал «готовый пакет доказательства — можно потрогать руками», а в репозитории этих файлов не было ни одного. Человек, скачавший проект, находил `demo/README.md` со списком отсутствующих файлов. Теперь `demo/` коммитится целиком, а `verifier/build.py` обновляет `demo/verify.html` вместе с остальными копиями — устаревший верификатор в примере был бы ловушкой.

**2. Блок «Проверка» в README не работал на свежем клоне.** Не было сказано, что перед прогоном надо поставить зависимости тестов и собрать три артефакта. У новичка падало шесть тестов, включая тот, который нарочно требует, чтобы собраны были все реализации. Блок дополнен и проверен дословно на чистом клоне: 111 + Go + 104 + 124 + 37, всё зелёное.

Попутно: `test_archived_files_are_read_only` падал под root — снятое право на запись ядро для root не проверяет. Само снятие права проверяется отдельной строкой, она и есть суть теста; под root добавлен пропуск. Иначе первый же прогон в контейнере показывал бы новому человеку красный тест на исправном коде.

### Что осталось сделать руками (не код)

- Пост с формулировкой «вот формат, вот пример, найдите дыру». Hacker News, r/crypto.
- Признак успеха и провала не меняются: issue с чужим сценарием — хорошо; сто звёзд и ноль issue — плохо.

## 11. Первое действие для следующей сессии

**Пауза.** Ничего не добавлять, пока не появится посторонний человек с реальным сценарием. Функции — только после того, как конкретный человек попросит.

### Когда пауза кончится, по убыванию ценности

**1. Разбор RFC 3161 в бинаре на Go.** Сейчас подпись штампа умеет сверять только Python и только через `openssl`; Go, TypeScript и браузер не умеют вовсе. Обещание «одна команда, ничего не устанавливать» выполняется поэтому лишь там, где есть Python и openssl, а флагманский верификатор — бинарь.

Оценка **пересмотрена**: писать разбор ASN.1 и CMS с нуля не нужно, есть готовые реализации — `github.com/digitorus/timestamp` (RFC 3161) и `infiniteloopspace/go_s-mime/timestamp` (проверка токена поверх CMS). Работа сводится к подключению, вшиванию набора корней (`buildtrust.py` дописать генерацией `verifier/go/trust.gen.go`) и тестам, а не к собственной криптографии.

**Развилка, которую надо решить до начала, — записана, не решена.** Бинарь перестаёт быть «только стандартная библиотека». Это заявленное свойство в README, PLAN.md и здесь, и держится на нём не эстетика, а **воспроизводимость сборки у стороны спора**: сегодня оппонент может собрать бинарь сам и сравнить отпечаток с опубликованным в `build.sh`. Замена свойства на «зависимости вкомпилированы, отпечатки опубликованы» — решение владельца, не разработчика. Отдельно в пользу решимости: кросс-машинный прогон (раздел 8) показал, что сборка и сейчас воспроизводится побайтово, так что терять есть что.

Обязательное требование к этой работе: **фаззинг на битых и враждебных `.tsr`**. Верификатор не имеет права падать ни на каком вводе — только возвращать вердикт. Это уже записано в «не сломать при правках», но для разбора ASN.1 оно из правила становится главным риском.

Побочная выгода, которая может оказаться решающей: `x509.VerifyOptions.CurrentTime` позволяет строить цепь **на момент штампа**, а не на текущий. `openssl ts -verify` так не умеет — см. раздел 9.

**2. Прогон на живом S3 с Object Lock.** Единственное непроверенное место в предложении по сохранности.

**3. OpenTimestamps** — с разрешения владельца, потому что публикация необратима.

**4. Усиление `test_tampering.py`** — параметризовать по типу пломбы (см. раздел 4).

**5. Шифрование значений полей** — снимает противоречие вычёркивания и WORM. Версия 2 формата, не раньше первого чужого пользователя.

## Не сломать при правках

- **`FORMAT.md` прав, код подчиняется.** Расхождение — дефект кода, не документа.
- **Векторы пересобираются побайтово.** Изменились после `genvectors.py` — значит изменился формат, и это должно быть осознанным решением с повышением версии.
- **Три состояния, а не два.** «Пломбы нет» ≠ «пломба не сходится» ≠ «пломба стоит, но не подтверждена». Трижды за проект это путали: дважды получалось ложное обвинение исправного журнала — худший отказ, какой этот продукт может выдать, — а на третий раз недоговорка в другую сторону (см. раздел 6). Ошибаться здесь нельзя ни в одну сторону: занижение обесценивает исправный журнал, завышение обесценивает весь инструмент.
- **Верификатор не имеет права падать.** Он обрабатывает файл от противоположной стороны: пределы разбора (512 записей, 64 МиБ на запись, 128 МиБ всего), отказ по именам с `..`, вердикт вместо трассировки.
- **Тихо терять запись нельзя.** Переполнение очереди — явная ошибка. `seq` присваивается в момент укладки на диск, а не вызова.
- **`test_anchor_load_bearing.py` и `test_tampering.py` — самые важные файлы в проекте.** Если они позеленели после правки верификатора, перепроверьте, что они не стали проходить впустую: сломайте верификатор нарочно и убедитесь, что они падают.
